# 国风·传统食物 (Chinese Traditional Food)

> Minecraft **26.1.2** + **NeoForge** 模组 · 许可证 **MIT** · 模组 ID `chinese_traditional_food`

添加中国常见的食材、调味料、厨具餐具、**八大菜系典型菜品**、
**早餐与特色小吃** 与 **传统节日食物**，并提供两条并行的烹饪路线：

* **电气线** —— 熔炉发电机 / 电动磨粉机 / 电动脱壳机，以及它们的 **3×3 放大版**（更快更省）；
* **灶火线** —— 电磁炉 + 炒锅 / 蒸笼 / 汤锅，插上电就能开火，随手可搭。

**最大的特点：做出来的菜能"摆出来"。** 不是背包里一格图标，而是端上桌的实体。

## 核心亮点：菜品摆放系统

只为每道菜注册一个方块会带来 100+ 方块 × 4 个 JSON 的资源爆炸，
所以这里走的是**通用摆放方块 + 方块实体**的路线：

```
餐盘 plate (1 份，素面白瓷)
      ┌─────┐
      │  ●  │
      └─────┘
```

方块实体记住"盘里是哪道菜"，客户端渲染器把**菜品自己的物品模型**画到盘子上。
**新增任何一道菜都不需要新代码、新模型、新方块 —— 它能吃，就能摆。**

| 手上 | 潜行 | 行为 |
| --- | --- | --- |
| 拿着菜 | 否 | 摆一份上去 |
| 空手 | 否 | 夹一口吃（那一份吃完自动清空） |
| 空手 | 是 | 把整份菜端回背包 |

判定"能不能摆"：带 `minecraft:food` 数据组件即可（原版食物也能摆），
或在 `#chinese_traditional_food:placeable_dishes` 标签里。

### 直接摆在地上的菜

不想用盘子时，拿着菜对地面右键就能直接摆下来（12 种三维器型）：

| 手上 | 潜行 | 行为 |
| --- | --- | --- |
| 空手 | 否 | 把整份端回背包（收拾桌子） |
| 空手 | **是** | 就地夹一口吃 |

两件事和餐盘刻意做得**不一样**，都有理由：

* **吃放在潜行上**：地上可能摆了一桌菜，右键应该是"收拾"而不是"动筷子"，
  否则收桌子时很容易误吃 —— 所以必须明确蹲下来才是吃。
* **吃完留下空盘子**：最后一口吃完时，那一格**变成一只空餐盘**
  （而不是直接消失）。摆一桌吃完之后桌上留下餐具，不会豁然空一片；
  空盘可以空手右键端走，也可以直接敲掉。

类似的还有**案板**：放上食材再用刀切，左边是待切的、右边是切好的。

```
案板 cutting_board
   ┌──────────────────┐
   │  待切食材 │ 成品   │
   └──────────────────┘
```

| 手上 | 案板状态 | 行为 |
| --- | --- | --- |
| 可切的食材 | 空 | 放上去 |
| 刀（`#knives`） | 有食材 | 切一刀，刀掉 1 点耐久 |
| 空手 | 有成品 | 取走成品（没成品则取回食材） |

切割表定义在 `tools/content_data.py` 的 `CUTTING`（由生成器写成 `ModCutting.java`），
匹配时**先具体物品、后标签**，所以「豆腐 → 豆腐丝」不会被「蔬菜 → 蔬菜丝」抢先命中。

## 作物：种子、植株与野生作物

真实感的关键一步是**"第一粒种子不能凭空合成"**。所以这个世界里有三样东西：

| | 是什么 | 怎么来 |
| --- | --- | --- |
| **野生作物** | 31 种长在野外的现成植株 | 自然生成在温带 / 热带 / 干旱 / 湿地四类群系里 |
| **种子** | 33 种，每一样都是**方块物品** | 采野生作物，或收割自家田里的成熟植株 |
| **植株** | 33 种，八个生长阶段 | 拿种子右键耕地 |

于是食材的来路是一条闭环：**野外采种 → 种进田里 → 收成留种 → 越种越多**。

### 种子就是方块物品

种子没有单独注册成 `Item` —— 它是植株方块的 `BlockItem`，右键耕地就种下去。
好处是"种子"这个概念在代码里只有一份，不存在"物品种子"和"方块种子"
两套东西要互相对齐。

### 掉落写在战利品表里

成熟（`age=7`）掉 **1 份收成 + 2~4 份种子**；没熟就拔只还你 1 份种子
（和原版小麦一个规矩），幸运附魔对两者都生效。

### 八种株型 = 264 张图，全部算出来

33 种作物 × 8 个生长阶段 = 264 张图（和原版一样**一阶一张**，
相邻两阶合并成一张的话，种下去会有两段时间完全看不出变化）。
这些图不是逐张画的，也不是拷贝现成素材 —— 而是**由几何 + 配色算出来的**：

**第一步，按"长什么样"归成八类**，每一类只写一次几何：

| 株型 | 作物 | 长什么样 |
| --- | --- | --- |
| 禾本 `grass` | 水稻 / 谷子 / 高粱 / 玉米 | 一丛主茎，顶端抽穗 |
| 豆科 `legume` | 黄豆 / 绿豆 / 红豆 / 豌豆 / 蚕豆 / 豆角 / 花生 | 矮丛上挂着豆荚 |
| 籽用 `seedpod` | 芝麻 | 细茎顶着蒴果串 |
| 块根 `root` | 萝卜 / 芋头 / 红薯 / 山药 / 姜 / 蒜 | 贴地羽状叶 + 露头的根 |
| 叶菜 `leafy` | 白菜 / 小白菜 / 菠菜 / 芹菜 / 香菜 / 韭菜 / 葱 | 抱心叶球 / 丛生叶 / 细长叶 |
| 茄果 `bush` | 辣椒 / 茄子 / 西红柿 | 小灌木，果挂着 |
| 藤本 `vine` | 黄瓜 / 冬瓜 / 丝瓜 / 苦瓜 | 蔓生的藤与大叶，瓜垂着 |
| 菌 `fungus` | 木耳 | 枯木上簸开的耳片 |

**第二步，让每种作物在成熟时结出自己的果** —— 这一步才是"认得出"的关键。
同一株型里的三种茄果（番茄 / 茄子 / 辣椒）就是靠果实分开的：

| 作物 | 收获物的图标种类 | 画出来的果 |
| --- | --- | --- |
| 番茄 | `veg_tomato` | 一嘟噜圆果 |
| 茄子 | `veg_eggplant` | 垂着一根长茄 |
| 辣椒 | `veg_chili` | 更细更短的一根辣椒 |
| 白菜 | `veg_napa` | 中间抱出一颗球 |
| 蒜 | `veg_garlic` | 白色的蒜头 |
| 芋头 | `veg_taro` | 紫色的芋头 |
| 高粱 | `ear_sorghum` | 红色的穗子 |
| 玉米 | `crop_corn` | 带苞叶的玉米棒 |

一共只写了 **12 种果实画法**（穗 / 棒 / 荚 / 球茎 / 露肩 / 叶球 / 丛生叶 /
细长叶 / 圆果 / 长果 / 瓜 / 菌耳），配上各自的配色与尺寸，
33 种作物就能一个个认出来了。

### 画法：**完全程序化生成**，不用任何现成素材

手写画法画过两版都不好看 —— 原因不在勤不勤，而在
**直接在 16×16 的网格上算坐标**：一条斜线只能画成楼梯，一片叶子只能是菱形。
现在换成两条关键做法，画质就上来了：

1. **超采样**。先在 **8 倍**分辨率的画布（128×128）上用浮点坐标画贝塞尔曲线
   与带锥度的笔画，画完再把 8×8 个小像素**平均**成一个最终像素。
   斜线与弧线的圆角因此都是平滑的 —— 抗锯齿在降采样那一步自然发生。
2. **按部位记深度**。每画一个部件就记一个自增深度号；降采样后，
   轮廓压暗一档、**部件交界**也压暗一档。叶子叠叶子时底下那片会自然
   退到后面去，而不是糊成一坨。

整个生成器只需要**三个图元**：

* **叶片** = 沿一条弧线、笔宽按剖面 `sin(π t^0.75)` 变化的笔画
  （根部窄、四成处最宽、尖端收拢 —— 这就是叶子的形状）；
* **茎** = 同一条笔画，只是笔宽从根到梢线性收细；
* **圆 / 椭圆** = 果实、穗子、耳片。

### 画风：小色板 + 有序抖动

超采样出来的颜色是**连续的**（抗锯齿产生了几百种中间色），
那不是像素画。所以最后一步要把整张图**压回一张小色板**：

1. 为每个像素在**多个色板**（叶 / 果 / 木）里挑最近的那个；
2. 用它的亮度在色板里定位成一个 0~1 的连续值；
3. **带 Bayer 4×4 抖动地**量化成 4 档 ——
   于是渐变变成"两三种颜色交替"的图案：远看是渐变、近看是像素；
4. 再看它是不是轮廓 / 部件交界 / 受光面，在色板里上下挪一档。

色板本身也做了两个刻意的选择：

* **底面压得够暗**（0.54 倍）—— 最暗那一阶直接当**轮廓线**用，
  不必额外描一圈黑边；
* **顶面只提一点点**（1.28 倍）—— 提太多会变成刺眼的高光，
  像素画的高光靠"位置"（左上边缘）而不是靠"更亮"。

另外两种"柔和"来自：**降饱和**（程序的绿容易荧光，往灰里混一点
就变成草地的绿）与**色阶间距均匀**（0.54 / 0.79 / 1.03 / 1.28）。

配色取自**收获物**，但不能整株照搬（否则番茄的叶子会是红的）：
叶色在一个基准绿上转一点色相、并按收获物**深浅**微调
（深色作物如木耳、茄子，叶子也跟着深一点）；
而**穗 / 果 / 露出的根肩直接用收获物本身的颜色** ——
所以红番茄、紫茄子、白萝卜都体现在果实上，而叶子始终是叶子。

### 五个踩过的坑

* **覆盖阈值不能定高**。一像素宽的叶子斜穿过一个输出像素时，
  在 8×8 的超采样里只盖住 15~25% 的子像素。阈值定在 0.42 会把细叶
  整条吃掉，植株就"秃"了。定在 0.20 细叶能活，而抗锯齿仍然有效。
* **不要重复翻转 y**。绘制时已经把"世界 y（0=地面）"翻成"图像行"了，
  降采样时若再翻一次，整株植物会**上下颠倒** —— 根长在头顶、穗垂在土里。
  这个 bug 是 dump 像素才发现的（肉眼在缩略图上看不出来）。
* **叶长得跟高度走**。藤本的叶长一开始写死了 `2.4 + 0.35i`，
  结果黄瓜整株只有 5 格高（叶子全趴在地上）。改成 `h * (0.42 + 0.11i)` 才对。
* **色板要按"就近"归类，不能按色相**。一开始用"绿系归叶、暖系归果"，
  结果木耳的棕褐色木头被归进了（近乎全黑的）果色板，那一截木头直接变成一块黑。
* **全黑的作物要提亮**。木耳本身近乎全黑，16×16 里一片黑就只剩一坨。
  耳片要拉到"深红褐"才能既看出是木耳、又还是暗色调。

### 种子叫什么名字，按农民嘴里的来

不是机械地"作物名 + 种"，而是每种用真实的留种叫法：

| 种子 | 为什么不叫"XX 种" |
| --- | --- |
| 玉米粒 | 玉米播种用的就是玉米粒本身 |
| 花生仁 | 花生是把荚里的仁剥出来种的 |
| 蒜瓣 | 种蒜就是埋一瓣蒜 |
| 芋子 | 芋头留种用的子芋 |
| 红薯秧 | 红薯靠插秧，不是撒籽 |
| 山药嘴子 | 山药的"龙头 / 嘴子"就是种 |
| 白菜籽 / 萝卜籽 / 芹菜籽 / 葱籽 | 这些真的就是籽 |

### 野生作物怎么生成
用的是原版的"三层世界生成"，所以"长在哪、多稀罕"全是数据说了算：

```
biome_modifier（加到哪些群系）
    └─ placed_feature（按概率筛区块、取点、落地表、试长几株）
           └─ configured_feature（具体放哪个方块）
```

最里面那层带 `minecraft:would_survive` 谓词 —— **下面不是土就直接放弃**，
所以野生作物不会长在石头上，也不会浮空。

## 食材包装方块：一袋米、一箱菜
参考农夫乐事的稻米袋 / 卷心菜箱：**每种原材料都有一只自己的袋 / 箱 / 缸**，
里面装 9 个散装食材，一共 95 种。

<H3>两句话定下了这两套造型</H3>

> "米袋这些能不能做成**完整的一整个方块**，但是材质贴近于**羊毛和布袋**"
> "萝卜箱之类的能不能做成**类似于原版木桶的形式（直接套用这些材质）**"

所以模型全部退回原版那套最简单的写法（**不写 elements，只用 parent**）：

| 样式 | 模型 | 说明 |
| --- | --- | --- |
| **袋** `bag` / `sack` | `cube_bottom_top` | 一整块**麻布**（细织纹 + 轻绒感），顶面是**扎口** |
| **箱** `crate` | `cube_bottom_top` | 侧壁与桶底**就是用原版木桶的贴图**，顶面 = 原版桶顶的木框 + 框里铺满的货 |
| **缸** `jar` | `cube_bottom_top` | 缸身**就是用原版陶罐的贴图**，顶面是照着同色画的盖子 |
| **压块** `brick` | `cube_bottom_top` | 一整块压实料，顶面有一圈模具压边 |

这么改的收益不只是简单：

1. **是完整方块** —— 能当建材码墙、能直接叠，格子之间不漏缝；
2. **装的是什么全由顶面表达** —— 侧视一律干净，不用把内容物画到四个侧面上；
3. **没有内嵌盒子了** —— 上一版为了"立体感"堆了十几个盒子，代价是共面闪烁、
   顶面贴图被斜面拉伸；现在从根上没这个问题。

<H3>三个画贴图时的坑</H3>

* **完整方块的贴图不能描边**。描边是给"有透明背景的图形"用的；
  整张不透明的方块贴图如果也描边，相邻两块之间会浮出一道**网格线**，
  本来该连成一片的货架就变成了一块块瓷砖。
* **箱里的货要按"框内区域"重新布局，不能先画满再裁**。裁的话三排果子
  会被切成"中间一坨"，根本不像番茄。所以 `contents()` 多了个 `inset` 参数。
* **布纹的密度差一倍就是两种东西**。16×16 上 4 像素一道织纹是"粗麻绳"的量级，
  看着又粗又脏；改成 2 像素一道、色阶从 5 加到 6、绒感抖动减半，
  才像布袋或羊毛。

<H3>两处“直接套用原版材质”是怎么做的</H3>

模型里引用 `minecraft:block/barrel_side` 只是“贴了一张原版图”；
难的是**我们自己生成的顶面要和它同色**。做法是把原版贴图的像素读进来：

* **箱顶**：直接以 `barrel_top` 为底（它本来就是"木框 + 中间一个圆盖"），
  把中间那个圆窗换成货。木框的像素就是原版的像素，当然和桶身同色。
* **缸盖**：从 `entity/decorated_pot/decorated_pot_side` 量出陶土色，（注：
  陶罐贴图在 `entity/` 下，但方块模型的贴图引用就是 `textures/` 下的路径，
  所以照写 `minecraft:entity/decorated_pot/...` 即可。）

取原版贴图由 `tools/vanilla_extract.py` 负责（从反编译产物里的客户端 jar 里拿，
缓存到 `tools/downloads/vanilla/`）。素材来自玩家自己的游戏本体，不随本模组分发。

| 样式 | 用在哪 | 长什么样 |
| --- | --- | --- |
| **麻袋** `bag` | 米 / 各种粉 | 满格鼓腹 + 顶上收口，**袋口露出内容物** |
| **布袋** `sack` | 各色豆子 / 果子 / 香料粉 | 矮胖、口是散开的，内容物堆到袋口之上 |
| **木箱** `crate` | 蔬果 / 干货 | **敞口**，四面木板只到箱高，**箱口直接铺满菜** |
| **陶缸** `jar` | 酱料 / 腌货 | 鼓腹收口 + 缸盖，盖顶看得见里面 |
| **压块** `brick` | 豆沙 / 豆腐 / 米糠 | 满格的压实块，中间一道模缝 |

清单写在 `tools/gen_compressed.py` 的 `COMPRESSED` 里；配错的那些不用手写——
`PACK_THE_REST` 只列“哪样东西装什么样式”，名字与配色直接取自 `content_data`，
所以以后往 `content_data` 里加一样作物，它自己就会多出一只箱子。

三个设计要点：

1. **模型全部铺满整格**（0~16）。码成一面仓库的墙、塞进箱子都整齐，
   格子之间也不会漏缝 —— 这正是那种"存货"的观感。
2. **一眼看得出装的是什么**：木箱是敞口的，箱口那面贴的就是内容物的俯视图
   （一根根胡萝卜 / 一颗颗番茄）；麻袋 / 布袋的袋口也露出内容物。
   内容物贴图按**形态**画：圆的果子画出轮廓与方形高光（能数出来），
   叶菜是几片叠着的大叶子，干货是不规则的块，谷物是码得整整齐齐的大颗粒。
3. **行为就是普通方块**：能放、能挖、挖了掉自己，**不需要右键取出**。
   想拆开就放工作台上用反向配方（9 个原料 ⇄ 1 个方块）。

### 画风：布纹 / 釉面 / 木桶

整体还是**平涂**（每种材质只用少量色阶，不做连续渐变），
但每种样式有自己的一套质感：

| 样式 | 质感怎么来的 |
| --- | --- |
| **袋** | 麻布 = 2 像素一道的经纬织纹 + 每像素约 14% 概率的绒感抖动 |
| **缸** | 就是原版陶罐的贴图，不重画 |
| **箱** | 就是原版木桶的木板与铁箍，不重画 |
| **压块** | 4×4 的大颗粒，每颗自己上亮下暗 |

**光影只做上下**（上亮下暗）——方块是方的，两侧压暗会变成"圆柱"。
这一条和"鼓起来的东西"（比如箱子里的果子）不一样，后者才用四向压暗。

配色直接取自 `content_data.PALETTES`，所以内容物一改颜色，袋子跟着变。
`python tools/preview_compressed.py` 会同时输出等轴测图与放大贴图对照板。

## 电力系统：熔炉发电机 + 两台加工机

现实里的水磨、碾米机太大，做成多方块以后操作又碎、搬运又麻烦，
所以最终统一改成**单方块电力设备**：每台机器只占一格，靠 FE 电力驱动。

| 机器 | 作用 | 耗电 / 发电 |
| --- | --- | --- |
| **熔炉发电机** | 烧原版燃料发电，向四周 6 个方向推电 | 40 FE/t，内部缓冲 4000 FE |
| **电动磨粉机** | 小麦→面粉 / 稻谷→大米（磨粉规则） | 10 FE/t |
| **电动脱壳机** | 带壳谷物脱壳 | 10 FE/t |

### 加工节奏：8 个一批，10 秒一批

两台加工机的节奏是刻意做成"整批"的，而不是一个一个磨：

* **每批 8 个**（`MachineEnergy.BATCH_SIZE`），**每批 200 tick = 10 秒**；
* 每 tick 消耗 **10 FE**，所以一批 2000 FE；
* 电不够时进度**原地冻结**（不倒退、不浪费），补上电继续；
* 输出槽放不下 8 个就先做放得下的数量（`plannedBatchSize()`），
  副产物按每个物品单独判定，机器上方满了就掉在地上。

### 界面

两块界面都是**标准的 `AbstractContainerScreen` + 贴图**，只画进度与电量。
踩过的两个坑都写在代码注释里了：

* **`blit` 的 textureWidth/Height 必须等于 PNG 尺寸**。引擎按
  `u / textureWidth` 归一化 UV，PNG 是 256×256 却传 176，整张界面就会缩放错位；
* **"满帧"必须画在面板之外**。面板是整张贴上去的，画在面板里的东西一开始就可见 ——
  原来把满箭头画在空箭头正下方，结果 0 % 进度时箭头看起来已经是满的。

所以贴图统一 **256×256**：左上 176×166 是面板，`x ≥ 176` 是动态部件的满帧条带
（`ARROW_FULL=(176,0)`、`FLAME_FULL=(176,20)`、`ENERGY_FULL=(176,40)`）。
`tools/preview_gui.py` 会按同样的 blit 规则合成 0 % / 中途四张界面图，
改坐标时先看它，比开客户端快得多。

### 机器模型：不是方块，但也不是多方块

三台机器都是**带腿的实体造型**（磨盘、料斗、烟囱、散热片、铆钉），
由 `tools/machine_models.py` 生成 24～32 个元素的模型：

* 摆在地上时**腿下面留空**，看得出是"一台机器"而不是一块石头；
* 碰撞箱略小于整格（`MACHINE_SHAPE = (1,0,1)~(15,16,15)`），贴着走不别扭；
* 四个朝向由方块状态 `facing` 决定，旋转 / 镜像都正常（`AbstractFacingBlock`）；
* `noOcclusion()`：腿部留空处不会把邻居的面剔掉。

> 注意：26.1 里没有 `DirectionProperty`，`BlockStateProperties.HORIZONTAL_FACING`
> 就是 `EnumProperty<Direction>`；另外 `HorizontalDirectionalBlock` 带一个抽象
> `codec()`，直接继承会编译不过，所以 `AbstractFacingBlock` 是继承普通 `Block`
> 自己声明属性的。

## 灶火：九格锅 + 电磁炉

**146 道菜全部下锅做**，没有一道菜是用工作台拼出来的 —— 这才是"做菜"。
锅分三口，各管一类做法：

| 锅 | 管什么做法 | 有多少道 |
| --- | --- | --- |
| **蒸笼** `steamer` | 蒸（面点、糕点、甜食） | 39 |
| **汤锅** `soup_pot` | 煮（汤、羹、饭、酒饮） | 41 |
| **炒锅** `wok` | 炒 / 煎（炒菜、鱼肉） | 67 |

### 九格原料槽：备好料就走开

一口锅有 **9 个原料槽**（3×3）。九样东西往里一塞，它会**自己一道道做下去**：

* 每一 tick 在一堆槽位里找一道**材料齐了**的菜（`ProcessRecipes.findCook`）；
* 凑齐就开火，进度走完把**每样材料各扣一份**、产出一份；
* 同一种材料放好几份，就能连着做好几道 —— 不必守在旁边一遍遍开界面。

每道菜要什么、要多久，都写在 `tools/content_data.py` 里，
由 `dish_cook_plan()` 展开成 `ModRecipes.java` 的 `CookEntry` 表：

* **做法 → 锅**：`DISH_COOKER`（蒸→蒸笼 / 煮→汤锅 / 炒煎→炒锅）；
* **要多久**：`DISH_COOK_TICKS`（炖 260、汤 200、饭 220、蒸 180、甜 160…）；
* **要什么料**：按做法给一组四样（`DISH_RECIPE_MATERIALS`），
  想精确到某道菜的用料就写 `DISH_COOK_OVERRIDE`（麻婆豆腐、腊八蒜就是这么写的）。

所以**加一道新菜只要在 `DISHES` 里填一行**，锅谱会自动跟上。

### 电磁炉：电换火

锅自己**不烧燃料也不存电**：正下方放一台**电磁炉**就行。
电磁炉是个完整的单方块，靠 FE 供电，只在**上面的锅确实有活要干**时
才抽电（25 FE/t），同时把 `powered` 方块状态点亮（面板亮一条灯带）。

这条设计把"灶"和"锅"拆开了：一个灶带三口锅，锅想搬到哪就搬到哪；
锅那边一行电力代码都不用写 —— `hasPower()` 只问"正下方热不热"。

### 界面上的"电量条"其实是热度

锅的界面比电动机器少一个概念：那根竖条在有火时就是满的。
`ProcessorMenu.isHeatPowered()` 为真时界面换成"热度 / 无火"的文案，
槽位布局也换成九格版（`GRID_INPUT_X/Y/STEP` 与 `texture_machines.cooker_gui()`
必须和 Java 那边三处坐标一致 —— 有一处对不上，点击就会偏格）。

最初蔬菜是"同类的共用一个画法"，于是 5 种瓜（黄瓜 / 冬瓜 / 丝瓜 / 苦瓜 / 茄子）
形状一模一样、4 种叶菜（白菜 / 小白菜 / 菠菜 / 香菜）只差颜色 ——
玩家根本认不出来。现在改成 **一种作物一套画法**（`tools/crop_icons.py`）：

| 作物 | 辨识特征 |
| --- | --- |
| 黄瓜 | 深绿、纵向浅色条纹 + 刺瘤 |
| 冬瓜 | 深青皮、胖乎乎、一层白霜 |
| 丝瓜 | 细长、三条纵棱、一端留干花 |
| 苦瓜 | 短胖、青黄绿、满身瘤皱 |
| 茄子 | 紫皮、一条高光带、绿萼 + 短柄 |
| 豆角 | 细长弯曲、能看出里面豆粒的鼓包 |
| 白菜 / 小白菜 | 紧实叶球 / 长白柄 + 一小把亮绿叶 |
| 菠菜 / 香菜 | 深绿尖叶摊成扇形（红根）/ 羽状裂叶 |
| 韭菜 / 蒜苗 / 葱 | 细长扁叶 / 宽扁叶 + 根部一瓣蒜 / 白葱头 + 绿管 |

### 玉米、米粒、豆子、种子

* 米粒 / 豆子 / 种子共用 `TI._draw_bean()` 这个"椭球粒"基元（带种脐），
  靠 **长宽比 + 数量 + 排列 + 配色** 区分：大米细长、糯米圆短、小米极小；
  芝麻扁、玉米是金黄的楔形粒；
* 叶菜 / 茎菜的叶片由 `_leaf()` 生成：沿一条可弯曲的轴线拉出锥形轮廓，
  再叠中叶脉与叶缘高光；
* 瓜类由 `_body()` 生成：`path(t)` 给弯曲轴线、`half(t)` 给粗细微调，
  表面花纹（条纹 / 瘤点 / 白霜）全部写在 `shade(t, s, x, y)` 回调里。

### 为什么农作物用 64×64

这些形体的辨识度全在细节上（叶脉、瓜棱、瘤点、种脐），16×16 根本画不下。
所以 `crop_icons.PAINTERS` 里的 kind 一律 **64×64**，其余物品仍是原版的 16×16 ——
Minecraft 的图集本来就允许一张图里混着不同尺寸的贴图。
用 `python tools/preview_crops.py` 可以直接出一张对照表，专门用来检查"哪些长得太像"。

### 种子

所有能种的作物都配了种子（33 种），而且**种子和它的作物长得不一样**：

* 谷物种子是带壳的稻粒 / 极小的谷粒 / 金黄的玉米粒；
* 豆类种子直接用那颗豆子（本来就是播种材料）；
* 瓜类 / 茄科 / 十字花科的种子按家族的**真实籽形**分开画
  （扁椭圆 / 淡黄扁圆盘 / 红褐小圆籽 / 带刺小球 / 黑色三角 / 细长小籽…）；
* 姜种带芽、蒜种是单瓣、红薯秧与山药嘴子各画各的、木耳菌种是一袋木屑菌包。

## 三维模型：为什么不用渲染器

菜品摆在地上、摆在盘里，用的都是**标准的方块模型 + 方块状态**
（原版的蛋糕、南瓜派、营火也是这个路子），而不是自定义渲染器：

* 只注册**一个**方块 `placed_dish`，靠 `shape` 属性在 12 种器型间切换；
* 12 种器型（碗 / 盘 / 大盘 / 砂锅 / 鱼盘 / 饺子 / 月饼 / 粽 / 糕片 / 酒盏 / 罐 / 方块）
  全部是**手写的立方体元素**，有真正的厚度与叠层；
* 每道菜的颜色由**方块着色**（`BlockTintSource`）按菜系配色染上去 ——
  和原版给树叶 / 草 / 药水上色是同一套机制。

“怎么用立方体画出圆”——`tools/dish_models.py` 里的 `_oct()` 把一个圆
**精确拆成 3 个互不重叠的矩形**（拼成八边形），再沿 Y 一层层收缩堆叠，
就有了圆润的盘沿与碗腹。共享边界上的两个面法线相反，背面剔除自动处理，
不重叠、不闪烁，也不需要任何旋转元素。

器皿（餐盘 / 大拼盘 / 案板）的三维模型由 `tools/display_models.py` 生成，
餐盘做成“圈足 + 盘腹 + 翘起的盘沿”，盘心比盘沿**低 0.8 像素** ——
菜是“盛”在盘子里，而不是浮在一块板上。

### “模型多大就占多大”

两套东西都遵守这条规则，只是源头不同：

* **摆在地上的菜**：`dish_models.bounds(shape)` 从生成的模型元素里**实测包围盒极值**，
  写进 `DishPlacement.BOUNDS`，Java 端直接拿它建 `VoxelShape`；
* **餐盘 / 大拼盘 / 案板**：碰撞箱写在方块类里，与 `display_models.py` 的模型边界一一对应
  （餐盘 `0.8..15.2 × y0..3.35`、拼盘 `y0..2.35`、案板 `0.4..15.6 × y0..1.9`）。

所以碰撞箱与看得见的模型**永远一致**：盘子只有 0.2 格高，能踩上去、
不会“上台阶”，也不会挡住邻居的贴面剔除。
大拼盘两侧的提手在模型里伸到了格子外面，但碰撞箱**不外扩** ——
否则会把相邻格子咬掉一块。

> 踩过的坑：不写 `getShape` / `getCollisionShape` 时，方块默认占满一整格。
> 一个 3 像素高的盘子却有一格高的碰撞箱，走上去就像上台阶，非常别扭。

### 菜为什么要绕 X 轴转 -90°

原版物品贴片是画在 **XY 平面** 上的（见 `ItemModelGenerator`：
几何范围 x 0~16、y 0~16、z 7.5~8.5），所以 `ItemDisplayContext.FIXED`
下物品是**竖立**的。原版营火、地面上的展示框都要额外转一下才会放平。
这里采用和“朝上的展示框”完全一致的写法（净旋转 `Rx(-90)`），
菜才会正面朝上、方向正确地躺在盘里（见 `PlateBlockEntityRenderer`）。

本仓库**只包含 Java 代码与 resources**（不含 `build.gradle`、Gradle Wrapper）。
使用方式：

1. 打开 <https://neoforged.net/mod-generator/>，填：
   - Mod name: `国风-传统食物`，Mod id: `chinese_traditional_food`
   - Package: `com.ctf.chinese_traditional_food`
   - Minecraft version: `26.1.2`，Gradle plugin: `ModDevGradle`
   - 下载并解压。
2. 把本仓库的 `src/main/java`、`src/main/resources`、`docs`、`tools` 覆盖进去。

## 纹理：原版分辨率的 16×16

默认就是**原版分辨率的 16×16**（也能 `--size 64` 出高清版），**风格没有变**：

| 规范 | 做法 |
| --- | --- |
| 边缘 | 逐像素直接写，**不做** 超采样 / LANCZOS / 高斯模糊 —— 抗锯齿会让材质发糊 |
| 渐变 | 每种材质只用 6~8 档亮度，档间用 **Bayer 4×4 有序抖动**过渡（像素画经典手法） |
| 质感 | 叠加确定性逐像素噪声，模拟苔痕/木纹/釉面颗粒 |
| 光照 | **不烘焙方向光** —— 方块进游戏后由引擎按面打光（顶 1.0 / 南北 0.8 / 东西 0.6 / 底 0.5），
顶面贴图只画器皿自身的弧度明暗，否则会双重变暗 |
| 平铺 | 方块贴图左右上下自洽，连续摆一排无硬接缝 |
| 物品图标 | 透明背景 + 右下压暗一档做体积感，与原版食物图标一致 |
| 树叶（方块） | 照原版分寸：镂空 **约 33%**、**不用半透明**、明度只 4 档 |
| 树叶（物品） | 方块贴图三成是洞，**不能直接当图标**；另画一张实心的一枝叶 |
| 树叶形状 | 每棵树给叶形 / 排列 / 片数 / 宽长比 / 特征（见下） |
| 木制品 | 13 种树各一套五色，色相**故意拉开**（李灰白…柿近黑） |
| 包装 | 编织袋染色 70% + 顶部麻绳；木桶板色跟内容物；箱顶木框引原版 |

### 配色来源

木色不是拍脑袋定的，而是从 **CC0 公有领域素材**里提取的：

1. 抓取 [Kenney Pixel Platformer Food Expansion](https://kenney.nl/assets/pixel-platformer-food-expansion)（CC0）
   与 [OpenGameArt 16x16px Food Items](https://opengameart.org/content/16x16px-food-items)（CC0）；
2. 量化后按 HSV 筛出「棕橙」候选（色相 18~46 度）；
3. 取候选的**色相中位数**作为木材色相，再按受控饱和度生成四档亮度阶梯。

见 [`ATTRIBUTION.md`](ATTRIBUTION.md)。
